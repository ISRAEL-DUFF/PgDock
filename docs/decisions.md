# Implementation decisions

Choices made while building, where the code departs from or fills a gap in
the [V1 specification](../PGDock%20—%20V1%20Specification%20&%20Build%20Plan.md).
The spec's own decisions log is §16.

## M1 — Shared-tier provisioning

| # | Topic | Decision | Why |
| --- | --- | --- | --- |
| 1 | First node | The shared cluster is registered from `PGDOCK_SHARED_ADMIN_URL` at startup, as a node with one shared instance. Its `pgdock_admin` credential is stored encrypted in `nodes.pg_admin_secret`. | Node registration through agents is M4. This keeps M1 usable on a single VPS. It is idempotent, so it also picks up a changed admin password. |
| 2 | Schema adjustments (migration 00002) | `nodes.private_addr` is `text` (hostnames allowed). `nodes.agent_cert_fp` is nullable until an agent registers. `instances` gains `admin_host`/`admin_port`. `projects.storage_target_id` is nullable until M3. | Compose service names aren't IPs. The control plane and the poolers can reach a cluster at different addresses (a published port in dev). Storage targets come with backups. |
| 3 | Password handoff for the smoke test | The create and rotate operations carry the new password, encrypted with the master key and bound to the project and purpose, in `operations.params.secrets`. The queue scrubs `params.secrets` when the operation finishes (success or failure), and the API never returns it. | §5.3 says passwords are never stored reversibly. But §6.1 step 5 smoke-tests the pooler as the new role, which needs the plaintext, and an operation can run in another process or after a restart. The ciphertext exists only while the operation is pending. |
| 4 | Pooler file layout | pgdock-server writes `databases.ini` and `userlist.txt` into `PGDOCK_POOLER_CONFIG_DIR`. Each PgBouncer's static `pgbouncer.ini` sets `auth_file` to that `userlist.txt` and ends with `%include` of `databases.ini`. The directory is mounted, not single files. | Pool mode and ports differ per pooler; routes and users are shared. An atomic rename only shows through a directory mount. |
| 5 | Admin console user | The admin console user's SCRAM verifier uses a salt derived from the master key (`Keyring.Derive`), so it is identical across syncs. | Keeps the auth file byte-identical when nothing changed, without storing plaintext. |
| 6 | Delete disconnects with `KILL` | Delete (and create rollback) issue `KILL <db>` on both poolers, remove the route and `RELOAD`, then `pg_terminate_backend` and `DROP DATABASE ... WITH (FORCE)`. | §6.2 says `PAUSE`, but in session mode `PAUSE` waits for clients to disconnect on their own. `KILL` drops them, which is what a delete wants. `PAUSE`/`RESUME` remain for promotion (M5). |
| 7 | One operation per project | Rotate and delete are refused (409) while another operation on the project is queued or running, checked under a row lock. | Keeps flows from interleaving, e.g. rotating mid-delete. |
| 8 | Not yet enforced | The final backup on delete waits for backups (M3) and is logged as skipped. (Re-authentication for delete landed in M2.) | Milestone order. |
| 9 | Cluster hardening at registration | `CONNECT`/`TEMPORARY` on `postgres` and `template1` are revoked from `PUBLIC`. `log_statement` and non-SCRAM `pg_hba.conf` network rules are reported as warnings. | Project roles must reach only their own database. Logging and `pg_hba.conf` are the operator's to change; the isolation suite checks them. |
| 10 | Attempts include crashed ones | An attempt cut short by a worker crash counts toward the kind's attempt limit. | Keeps a crash-looping operation from retrying forever. |

## M2 — Auth, TLS & the web UI shell

| # | Topic | Decision | Why |
| --- | --- | --- | --- |
| 1 | Claiming a fresh install | The setup wizard needs a one-time code that pgdock-server prints in its log (or `PGDOCK_SETUP_CODE`). | A freshly started control plane on a public IP would otherwise belong to whoever loads it first. |
| 2 | TOTP before the account exists | `/setup/begin` returns the TOTP secret but creates nothing; `/setup/complete` creates the owner only with a valid code. | Spec §7.2 enforces 2FA at first login; this way there is never an owner without it. |
| 3 | TOTP replay | Each operator's last accepted time step is stored; a code is accepted once, and only for a later step. | A code seen by someone else (shoulder, logs) cannot be reused within its 90-second window. |
| 4 | CSRF | Double-submit token (`pgdock_csrf` cookie and `X-CSRF-Token` header), plus a required matching `Origin` when the browser sends one, on every mutating `/api` request, including login. Cookies use the `__Host-` prefix when Secure. | Spec §7.2; `SameSite=Strict` on the session cookie is a second line. |
| 5 | Re-auth scope | Required for `DELETE /projects/{id}` today, within 10 minutes of a password + TOTP check. The UI asks for both inside the typed-confirmation dialog. | Spec §7.2 lists delete, in-place restore, master key rotation, and node removal; the others arrive with their features. |
| 6 | Audit log | Every mutating API request is recorded with its outcome (`success`, `failure`, `denied`), including requests refused for CSRF, authentication, or re-auth. Details never include passwords or codes. | Spec §7.5; refusals are the interesting part of an audit trail. |
| 7 | Guardrail changes | `PATCH /projects/{id}/settings` queues `apply_settings`, which re-applies role settings, re-renders the pooler, and issues `RECONNECT <db>`. | `ALTER ROLE ... SET` only affects new backends, and PgBouncer would otherwise keep serving pooled connections with the old values. The integration test caught this. |
| 8 | Pooler TLS | pgdock-server obtains the DB hostname's certificate itself (certmagic, HTTP-01); Caddy forwards `/.well-known/acme-challenge/` for any non-UI host on :80 to it, and certmagic is pointed at pgdock-server's own port so it never binds :80 itself. The pair is written to the pooler dir and the poolers `RELOAD` (verified to swap certificates without a restart). Until a CA certificate exists, a self-signed one stands in; IP addresses and `localhost` stay self-signed. | The DB hostname is set in the wizard, after Caddy has started, and PgBouncer needs files on disk. Spec §3.3 allows HTTP-01 or DNS-01. |
| 9 | Clients must use TLS | Both poolers run `client_tls_sslmode = require`; connection strings default to `sslmode=require`. | Spec §3.3. |
| 10 | One uid for server and poolers | The pgdock-server image runs as uid 70, PgBouncer's uid, so the generated files (including the TLS key) stay 0640. | Avoids world-readable keys in the shared volume. |
| 11 | Session refresh in the UI | Sign-in and setup write the session state the server returns straight into the query cache. | Invalidating an unobserved query does not refetch, which sent freshly signed-in users back to `/login`. The browser test caught it. |

## M3 — Agents, backups, restore & import

| # | Topic | Decision | Why |
| --- | --- | --- | --- |
| 1 | Backup encryption | Our own format (`internal/backupfmt`) rather than age: AES-256-GCM over 64 KiB chunks (STREAM: counter nonces, a last-chunk flag in the associated data), with a random per-object key wrapped by the backup key in the header. `backups.key_wrapped` keeps a copy. | No extra dependency or key format for operators; truncation, reordering, and a wrong key are all detected; the backup key never touches object data directly. |
| 2 | Backup key | Separate from the master key, generated in the wizard, and only stored sealed with the master key. Confirming needs the full key pasted back (or the file loaded); the fingerprint shown in the UI is not accepted. Re-downloading needs re-authentication. | Spec §7.3, §15: the key must be proven to exist offline. A losable master key must not also lose the backups. |
| 3 | Agent trust | pgdock-server runs a private CA (key sealed with the master key). Agents get `CN=node:<id>` certificates at registration, and the server pins their SHA-256 fingerprints; the server's client certificate is `CN=pgdock-server`. Registration exchanges a CSR and a one-time token (hashed, 24h), or `PGDOCK_AGENT_BOOTSTRAP_TOKEN`, which only claims a node that has no agent yet. | Spec §3.2: mTLS with no external PKI. Pinning means a CA compromise alone cannot impersonate a registered agent. |
| 4 | Data path | Agents stream dumps straight to S3 (multipart) and restores straight from it, encrypting and decrypting on the node; storage credentials and keys travel per request over mTLS and are not stored on agents. Postgres passwords reach `pg_dump`/`pg_restore` through the environment. | Spec §6.3: client-side encryption, no plaintext through the control plane, no secrets in process listings. |
| 5 | Restore semantics | `pg_restore --no-owner --no-acl --role=<owner> --single-transaction --exit-on-error`. A retried restore into a new project starts from a recreated empty database. | Every object ends up owned by the project role; a failed restore leaves nothing half-applied. |
| 6 | In-place restore | The project moves to `restoring`; the pooler `KILL`s its clients (new ones wait until `RESUME`), the database is dropped and recreated, the backup restored, and the route resumed. A safety backup is taken first (once per operation); if the restore fails, the safety backup is restored the same way. Re-authentication and the typed name are required. | Spec §6.5. `KILL` rather than `PAUSE` for the same reason as M1 #6. |
| 7 | Scheduling | Every server ticks each minute under `pg_try_advisory_xact_lock`. A project's nightly backup is due at the window start (`PGDOCK_BACKUP_HOUR` UTC) plus a stable offset from a hash of its ID (`PGDOCK_BACKUP_JITTER`, default 2h); "already done" means a `backup` operation exists since the window opened. Projects with an operation in flight are skipped until the next tick. | Spec §6.3 jitter; safe with several servers; never interleaves with a restore or delete. |
| 8 | Retention | The newest backup of each of the 7 most recent days that have one, then the newest of each of the 4 ISO weeks before those; the newest backup is always kept. Final and safety backups expire after 30 days, independent of retention. | Spec §4.3 (7 daily + 4 weekly), with gaps in the schedule not shortening the history. |
| 9 | Final backup without storage | A delete on an install with no storage or no backup key logs "final backup skipped" and proceeds; `skip_final_backup` skips it explicitly. | Deletes must work on a fresh install; the log and the UI say what happened. |
| 10 | Restore test | Weekly, for a random active project with a backup: the latest backup is restored into a scratch database (`pgdock_restore_test_*`), every table counted, and the database dropped. The result is the operation's status and log, shown in Settings. | Spec §6.5. Alerts arrive with M6; until then the Settings card and operation history show failures. |
| 11 | Metadata self-backup | Nightly, an agent dumps the metadata DB (`PGDOCK_METADATA_BACKUP_URL`, default `PGDOCK_DATABASE_URL`) into `metadata/` with the same encryption and retention. `pgdock-agent decrypt` turns an object back into a `pg_dump` archive with just the key file. | Spec §11.6 and the runbook in [disaster-recovery.md](disaster-recovery.md). |
| 12 | Import source | The control plane runs the preflight and verification itself (read-only sessions), and the agent runs the copy, so both must reach the source. The connection string lives in process memory only, keyed by a random reference in the operation's params; after a server restart the import fails with "start it again". | Spec §6.8 notes: never written to the metadata DB. |
| 13 | What `pg_dump -n` leaves out | Before the copy, PGDock creates (as the admin) the allow-listed extensions the source uses, in the same schema (e.g. `extensions`), so defaults like `extensions.uuid_generate_v4()` restore. For Supabase sources it adds `auth.uid()`, `auth.role()`, and `auth.jwt()` (reading `request.jwt.claims` like Supabase) owned by the project role, and creates `anon`, `authenticated`, and `service_role` cluster-wide as NOLOGIN roles with no members. The copy continues past objects that cannot restore (e.g. a foreign key to `auth.users`) and lists them in the log. | Spec §6.8 says policies on Supabase roles are kept; they can only restore if the roles exist. Nobody can log in as or become the stand-ins, so they grant nothing. |
| 14 | Verification | Per-table row counts and sequence values in the chosen schemas are compared. A table missing on the target fails the import (and rolls the project back); differing counts are reported as a warning, since the source may still be taking writes. | Spec §6.8 step 5, without failing imports from live sources. |
| 15 | Testing the Supabase path | Tests import from the `supabase/postgres:17.6.1.003` image with a Supabase-shaped app (RLS policies on Supabase roles, `auth.users` references, extensions in `extensions`, a trigger, a second schema), connecting as its non-superuser `postgres` role like a hosted project, plus a plain Postgres 15 source. No hosted Supabase project is reachable from CI. | The M3 done-when names a real Supabase project; this is the closest reproducible stand-in. |

## M4 — Nodes & dedicated instances

| # | Topic | Decision | Why |
| --- | --- | --- | --- |
| 1 | Docker access | The agent talks to the Docker Engine API (v1.43) over the daemon socket with a small client of its own (`internal/docker`: images, volumes, containers, exec), not the Go SDK. | Spec §3.4 names the SDK; it brings a large dependency tree for the ten calls PGDock makes. The API is stable and versioned. |
| 2 | Instance image | `deploy/images/postgres`: `postgres:18` plus WAL-G v3.0.9 built from its pinned commit through the Go module proxy, without cgo, tagged `pgdock-postgres:18-walg3.0.9` (the agent's default). | Reproducible from the commit, no system packages or GitHub release downloads; one image for dedicated and agent-run shared clusters. |
| 3 | WAL-G encryption | OpenPGP (`WALG_PGP_KEY`), with the key derived deterministically from the backup key (HKDF → seeded X25519 key, fixed creation time). | Spec §7: backups are encrypted before upload. libsodium needs cgo; a derived key keeps "the backup key alone restores everything" true for physical backups too. |
| 4 | Where instances live | The agent creates `pgdock-<instance>` with a `pgdock-<instance>` volume, CPU and memory limits, `unless-stopped`, and joins `PGDOCK_AGENT_NETWORK` (reached by container name on 5432) and/or publishes on `PGDOCK_AGENT_PUBLISH` (an ephemeral port). `instances.host/port` is what poolers and agents use; pgdock-server uses it too (`PGDOCK_DEDICATED_ADMIN_VIA=network`, the bundle) or the published port (`published`, dev and tests). | One host or many: the bundle shares a Docker network; a remote node publishes on its private address. |
| 5 | Volume size | `volume_gb` is recorded and drives the disk warning (80%); Docker local volumes cannot enforce it. | Spec §4.3 says "80% of volume" as a warning; hard quotas need a filesystem setup outside PGDock's control. |
| 6 | Instance credentials | Each instance has its own `pgdock_admin` (random password, sealed in `instances.admin_secret`). The agent passes it, the S3 credentials, and the WAL-G key as container environment. | Containers need them to archive WAL on their own. They are visible to root on the node, which already holds the data. Rotating storage credentials needs the containers recreated (not yet automated). |
| 7 | Restore into a new instance | The agent fills the new volume in a one-off container (`wal-g backup-fetch`, then `recovery.signal` and recovery settings in `postgresql.auto.conf`, with `restore_command` pointed at the source's archive), then starts the instance, which archives its new timeline to its own prefix. Once promoted, pgdock-server resets the recovery settings, renames the source's database and role to the new project's, and sets the new verifier. | Spec §6.5 (dedicated): base backup + WAL to a target time, into a new project, source untouched. Renaming keeps names globally unique for the poolers. |
| 8 | Making the target reachable | Before a recovery, pgdock-server runs a transaction with an XID on the source and `pg_switch_wal()`, then waits for `pg_stat_archiver` to show that segment. | Recovery to a time stops at the first commit after it and fails (Postgres 13+) if none is in the archive; this guarantees one, and that everything committed before the request is archived. |
| 9 | Base backups | `wal-g backup-push` runs through the agent right after a dedicated project is created and daily in the backup window (in place of the logical dump), followed by `wal-g delete retain FULL 7`; rows for backups WAL-G dropped are marked deleted. A base backup row restores as a recovery to its end. | Spec §6.4 and §4.3 (daily base + WAL, 7-day PITR). |
| 10 | Deleting a dedicated project | A final logical backup (kept 30 days, restorable into a shared project), then the container, volume, and WAL-G archive are removed. | Spec §6.2 step 4; the physical archive has no use without its instance. |
| 11 | Node roles and placement | Nodes are added in the UI (`POST /nodes` returns a one-time token and the command to run). The role (`shared`, `dedicated`, `both`; the bundle's local node starts as `both` via `PGDOCK_SHARED_NODE_ROLE`) decides where new projects go; restarts no longer reset it. Dedicated placement picks the healthy node with an agent running the fewest dedicated instances; shared placement the running shared cluster with the fewest projects on a node whose role allows it. | Spec §6.1 step 1 and §8.1 /nodes. |
| 12 | More shared clusters | A node's agent can run a shared cluster container (`POST /nodes/{id}/shared-cluster`), registered like the one from `PGDOCK_SHARED_ADMIN_URL`. | Multi-node shared placement without asking operators to install and wire Postgres by hand. |
| 13 | Removing a node | `DELETE /nodes/{id}` (re-auth) is refused while instances run there; otherwise the node is marked `removed` and its agent's certificate is no longer trusted. History stays. | Projects and backups keep referring to the node's past instances. |

## M5 — Promotion

| # | Topic | Decision | Why |
| --- | --- | --- | --- |
| 1 | Target instance | The dedicated instance is created first, with the project's role and the same SCRAM verifier, before anything is frozen. | The slow part (pulling, starting, health checks) happens while the app keeps writing; the password and URL do not change. |
| 2 | Freezing writes | `ALTER ROLE <owner> NOLOGIN`, then the poolers (`pooler.Freeze`), then `pg_terminate_backend` for the role's remaining sessions. The session pooler KILLs the database at once; the transaction pooler PAUSEs it (up to 10s, then KILLs). | `ALLOW_CONNECTIONS false` would also block `pg_dump`. PAUSE lets transaction-mode clients wait instead of failing, but on the session pooler it waits for every client to disconnect, which stalled the freeze for its full timeout. Session clients see one dropped connection and reconnect. |
| 3 | Copying | A full `pg_dump \| pg_restore` through the target node's agent, keeping owners and ACLs (`KeepOwners`), in one strict transaction. Roles that grants, policies, or ownership refer to are created first as NOLOGIN placeholders. | The project's own role owns its objects on both sides, so there is no `--role` rewrite to do; a missing role would otherwise fail the strict restore. |
| 4 | Verification | `pgverify.Compare`: every user table's row count and every sequence's value must match the frozen source; a mismatch fails the operation before the switch. | Spec §6.6: no lost commits. With writes frozen the counts are exact. |
| 5 | The switch | One transaction points the project at the instance, sets the tier and the dedicated defaults (connection limit ≥ 90, pool ≥ 20, disk warning at 80% of the volume), and records the source in `retired_databases`. Then the poolers are synced and RESUMEd, the project is set active, and a base backup is taken. | Everything after the commit is idempotent: a retry whose project already points at the target only runs the finishing steps. |
| 6 | Rollback | A failure before the switch restores LOGIN, RESUMEs the poolers, sets the project active, and destroys the target instance; after the switch, the operation finishes forward. | Spec §6.6: a failed promotion leaves the project where it was. |
| 7 | The source copy | Kept with `default_transaction_read_only=on` and the role NOLOGIN for 48 hours, then dropped by the hourly backup loop (`DropRetired`). The project shows the date (`retired_copy_until`). | Spec §6.6: a safety net for a short time, then reclaimed. |
| 8 | Downtime estimate | `5s + size / 40 MiB/s`, shown in the wizard (`GET /projects/{id}/promote`). | A conservative dump-and-restore rate on a small node; the measured freeze for a 10 MB project is under a second plus the copy. |

## M6 — Console, browser & metrics

| # | Topic | Decision | Why |
| --- | --- | --- | --- |
| 1 | Console identity | Sessions sign in as `<db>_console` (created on first use: LOGIN, NOINHERIT, connection limit 5, granted the owner role `WITH INHERIT FALSE, SET TRUE` and CONNECT on the database), then `SET ROLE <owner>`. Its password is derived from the master key; a failed login or `SET ROLE` re-creates or repairs the role and retries once. | Spec §8.5 says an admin connection plus `SET ROLE`, but a superuser session can `RESET ROLE`. This login reaches exactly the owner's privileges and nothing after a reset. No new secret to store; restores, promotions and key rotations heal on first use. |
| 2 | Read-only mode | One statement through the extended protocol, after `BEGIN READ ONLY; SELECT 1` (so the transaction can no longer be made read-write), then `ROLLBACK`. Read/write submissions use the simple protocol and may hold several statements. | A multi-statement string could `COMMIT` out of the read-only transaction; the extended protocol takes one statement only. |
| 3 | Cancel | The browser picks a query id; the session's `application_name` carries it, and cancel runs `pg_cancel_backend` on the matching backend. | Works from any pgdock-server, with no in-memory registry. A closed request also cancels its query. |
| 4 | Limits | Timeout 30 s by default (1 s to 5 min), statement and lock timeouts set per session; 1,000 rows per result (the rest are read and counted, not sent); cells over 64 KiB truncated; SQL up to 1 MiB. The console is refused while a project is not active, and promotion's freeze ends console sessions too. | Spec §8.5. Writes through the console during a promotion copy would be lost. |
| 5 | Audit | `project.console` per submission with the read-only flag, statement count and SQL error code; never the text. History is browser-local. | Spec §8.5. |
| 6 | Table browser | Runs in a read-only console session. Pages of 50, keyset on the primary key; tables without one page by `ctid`; views and partitioned tables by offset. Cursors are opaque (base64 JSON). | Spec §8.6. Same permissions as the console, nothing the project role cannot read. |
| 7 | Metrics collection | Every `PGDOCK_METRICS_INTERVAL` (1 min), one admin connection per instance reads `pg_stat_database` and `pg_stat_activity` (database size every 5 min), and the poolers' `SHOW POOLS`; TPS and cache hit ratio are deltas between samples. Node metrics come from the agent checks (every 30 s); the agent now also reports cumulative CPU ticks and disk bytes for CPU % and I/O rates. Points are upserted into the sample's minute. | Spec §8.7. Upserting by minute keeps several servers or restarts from duplicating points. |
| 8 | Downsampling | Hourly (and at start for the last 25 hours): averages of completed hours into `1h` points; 1-minute points kept 24 hours, hourly 30 days. The 7-day range adds averages of hours not yet downsampled. | Spec §8.7, no Prometheus dependency. |
| 9 | `/metrics` | Latest values as gauges `pgdock_project_*` and `pgdock_node_*` with id and name labels, for a signed-in operator or `Authorization: Bearer $PGDOCK_METRICS_TOKEN`. | Spec says "optionally protected"; project names are not public, so without a token it needs a session. |
| 10 | Top queries | Read live from `pg_stat_statements` in the project database (filtered to that database, without pgdock's own queries) when the project has enabled the extension. Console sessions are not tracked (`pg_stat_statements.track = none` on the console role). | The shared cluster preloads it; enabling it per project keeps the view opt-in. The list shows the app's workload, not the browser's catalog reads. |
| 11 | Extensions | `POST /projects/{id}/extensions` runs `CREATE EXTENSION … WITH SCHEMA public` as the instance superuser for allow-listed names the server has (`pg_available_extensions`), and records them in `projects.extensions`. | Spec §7.4. Most allow-listed extensions are not trusted extensions, so the project role cannot create them itself. |
| 12 | Charts | A small SVG line chart drawn from theme tokens instead of a chart library. | Four chart types; no dependency or CSP exceptions. |

## M7 — Alerts, hardening & release

| # | Topic | Decision | Why |
| --- | --- | --- | --- |
| 1 | Alert state | One `alerts` row per firing condition (unique on its key while firing), resolved in place; evaluated every 30 s. A condition that returns after resolving opens a new row. Evaluation that could not read every source resolves nothing. | Each transition is recorded once, whichever server sees it first; a database hiccup must not "resolve" a real problem. |
| 2 | Delivery | Firing and resolved notifications go to every configured channel; a failed one retries with backoff (1 min doubling, up to 30 min) under a one-minute claim. Webhooks are JSON, optionally signed `X-PGDock-Signature: t=<unix>,v1=<HMAC-SHA256 of "t.body">`. SMTP supports STARTTLS (required when chosen), implicit TLS, or none (local relay). Secrets are sealed with the master key. | Spec §8.8. The signature scheme is the common Stripe/GitHub shape receivers already verify, with a timestamp against replay. |
| 3 | Triggers | Spec §8.8's list, plus the metadata self-backup and a failed weekly isolation check. "Overdue" is 26 h without a successful backup; "unreachable" is 2 min since an agent last answered (`nodes.last_reachable_at`); project disk compares the latest size sample with the project's warning. | Spec §8.3 and §8.8 thresholds. |
| 4 | pg_hba.conf | The bundle's shared cluster accepts SCRAM logins only from the fixed addresses of pgdock-server, the agent, and the two poolers. Agent-run clusters and instances get `pg_hba.conf` from `PGDOCK_AGENT_DB_ALLOW` at initdb (default: the private ranges; the bundle: the same four addresses). | Spec §7.1 "accepts only the pooler and control plane IPs". |
| 5 | Isolation check | `internal/isocheck` checks a cluster's settings and `pg_hba.conf`, every project's role and database, and two throwaway tenants provisioned with the real create steps that try every cross-tenant move. CI runs it on the test cluster; pgdock-server runs it weekly per shared cluster as `isolation_check` (and on demand), and a failure alerts. | Spec §7.1 "CI + weekly on live nodes", with one implementation for both. |
| 6 | Failure fixes | A failed create rolls back even when a pooler is down (the config files are written; the pooler reads them when it starts). A backup attempt marks rows earlier attempts left `running` as failed, and an hourly sweep catches the rest. The agent's `pg_dump`/`pg_restore` die with it (`Pdeathsig`). | Found by the failure-injection tests (spec §13). |
| 7 | Pooler idle timeout | `server_idle_timeout = 30` on both poolers. | The load test showed every create's smoke test leaving idle server connections for 10 minutes; at ~250 projects they would fill `max_connections`. |
| 8 | Master key rotation | `pgdock-server -rotate-master-key` with the new key as `PGDOCK_MASTER_KEY` and the old in `PGDOCK_MASTER_KEY_PREVIOUS`: every sealed secret is re-encrypted in one transaction, then verified to open with the new key alone; sign-in challenges are dropped. | Spec §7.3. All-or-nothing, so a wrong key changes nothing. |
| 9 | Agent versions | pgdock-server sends no work to an agent of another major version (development builds match anything); health checks still reach it and the Nodes page says why. | Spec §11.3. |
| 10 | Audit log | Triggers refuse `UPDATE`, `DELETE`, and `TRUNCATE` on `audit_log`. | Spec §7.5 "append-only", enforced below the application. |
| 11 | Minor upgrades | Restart from the UI recreates a dedicated instance's container from the node's current image on the same volume. | Spec §11.3: rolling restarts pick up a rebuilt `pgdock-postgres` image. |
| 12 | Install guide as a test | `docs/install.md` marks the commands a reader runs; `make test-docs` (and CI's `docs-install` job) clones the commit, runs exactly those blocks with Pebble standing in for Let's Encrypt, then drives the setup wizard to a working database in a browser. | M7's done-when: an install from the docs alone must work. |
| 13 | Releases | A `v*` tag builds linux/amd64 and arm64 binaries (UI embedded), a source bundle, and SHA256SUMS, and publishes a GitHub release with that version's CHANGELOG section. The bundle builds its images from source. | Spec §11.5. |
| 14 | Dependency audit | `govulncheck` and `npm audit --audit-level=high` (web and e2e harness) on every push. | M7 dependency audit, kept current rather than one-off. |

## M8 — Users, organisations & access control

| # | Topic | Decision | Why |
| --- | --- | --- | --- |
| 1 | V1 data | Migration 00010 renames `operators` to `users` (the operator becomes `platform_admin`), creates a personal organisation per user, and moves every project into the platform admin's (an `existing-projects` organisation if there are no users). It has a full down migration. | V2 §2.6: V1 projects appear in the personal org unchanged. |

## M9 — Tenancy hardening, quotas & usage

| # | Topic | Decision | Why |
| --- | --- | --- | --- |
| 1 | Opaque names | New projects get `p_<10 base32>` databases and roles (`_owner`, `_ro`, `_console`, `_u_<6>`), no slug. `projects.db_name` stays the backend database name; V1 projects are renamed in place by a `rename_opaque` operation and keep their old name as `alias_db_name`, a pooler route to the new database, so their URLs keep working. | V2 §10.2. Keeping `db_name` as the backend name (the spec suggests a `backend_db_name` column) leaves every V1 code path that reaches the database correct; only the URL builder needs to know about aliases. |
| 2 | Switch credentials | "Switch to opaque credentials" creates a new opaque owner, `REASSIGN OWNED`s to it and makes the old owner a member that `SET role`s to it, so the old password keeps working through the grace period (7 days by default, 1–90). An `expire_legacy_credentials` operation then drops the old role and the alias route. | V2 §10.2: no flag day for apps. |
| 3 | `pg_stat_activity` | `REVOKE ... FROM PUBLIC` on `pg_stat_activity` and `pg_stat_get_activity(integer)` in every shared project database (they are per database, not per cluster). The driver compatibility suite (psql, pgx, node-postgres) passes without them. | V2 §10.2: other tenants' role and database names leak through it. |
| 4 | Quotas | Plans hold the limit keys; an org's overrides win key by key. Creation-time checks (projects, storage, operations in flight, console queries, connections) return 409 `quota_exceeded` with the limit, use and maximum. Console concurrency is counted per server. | V2 §10.3. |
| 5 | Storage enforcement | Every minute: warn at 90%, soft lock at 100% (`default_transaction_read_only` on the database), hard lock at 120% or at 100% when the node disk is 95% full. The hard lock makes the project's logins `NOLOGIN` (not `REVOKE CONNECT`) and ends their sessions; the console role is untouched, so owners can delete data and **Reclaim space** (`VACUUM (FULL, ANALYZE)` of one table). Locks lift at the next check below the threshold. | V2 §10.4. `NOLOGIN` leaves the console's own role working without a second grant scheme. |
| 6 | Reaper | Every 15 s on each shared cluster: statements running over 10 minutes are cancelled and sessions idle in a transaction over 5 minutes are ended; each is recorded and shown on the project's Metrics page. Ages are compared with the server's clock, so tests can move it. `temp_file_limit` is 2 GB per role. | V2 §10.4. |
| 7 | Per-org clusters | A shared cluster can be assigned to an org; that org's new projects go only to its clusters, and other orgs' never do. Moving existing projects onto an org's cluster is deferred (promote or restore instead). | V2 §10.5. |
| 8 | Dedicated allowance | Plans (and overrides) include a number of dedicated instances and their total vCPU, RAM and disk. Beyond it, Promote and New project make a dedicated request for the platform admin to approve or reject. The Unlimited plan has no limit. | V2 §10.6. |
| 9 | Suspension | Suspending an org makes its project logins `NOLOGIN`, removes its pooler routes, stops backups, and freezes the API to reads (403 `org_suspended`). Outbound disable is stored and shown now; it is enforced when outbound features arrive (M15). | V2 §10.7. |
| 10 | Break-glass | A platform admin opens a session (reason, up to 4 hours, step-up required) to act as an org admin; org owners and admins are emailed, every action is audited with `break_glass`, and the org sees a banner. Expiry uses the database clock. | V2 §10.7, open question 3: notify and audit, no owner approval. |
| 11 | Usage | Every completed hour: shared storage GB-hours (the hour's average size, GB = 10^9 bytes), dedicated vCPU, RAM and disk hours, and pooler transfer (deltas of `SHOW STATS`, baselines per server); backup GB-hours daily. A watermark in settings and an advisory lock make it resumable and single-writer; a first run backfills 8 days. Hourly rows roll up to daily after 90 days. | V2 §10.9. Nothing is billed; the CSV export is for operators who want to. |
| 12 | Org deletion | Owners request deletion; the org is frozen to reads for 7 days and can be cancelled. Then each project gets a final backup (kept 30 days) and is deleted, memberships and invitations end, and the org is marked deleted. Personal orgs cannot be deleted. | V2 §10.10. Account deletion and project export are deferred. |
| 13 | Isolation suite v2 | The nightly isolation check (was weekly) also checks for metadata leaks (other projects' names in catalogs and `pg_stat_activity`), quota bypasses (connection limit, `temp_file_limit`, `ALTER ROLE` and `SET` attempts) and that suspended or hard-locked projects cannot log in. | V2 §10.8. |
| 14 | PgBouncer | `server_login_retry = 2` (was 15 s): a login refused while a project was locked is retried soon after the lock lifts. | Found by the storage-lock test. |

## M10 — API tokens & CLI

| # | Topic | Decision | Why |
| --- | --- | --- | --- |
| 1 | Token format | `pgd_` + 32 random bytes in base62 (47 characters), stored as SHA-256 hex with an 8-character display prefix. | V2 §7.2: high entropy, so no slow hash; the prefix is for secret scanners and recognising a token. |
| 2 | Scopes | Hierarchical: `write` includes `read`, `admin` requires `write` (stored as the full set). Each authz action names the scope it needs (`authz.ScopeFor`); the check runs after the user's own role check, so a token never exceeds its user. | V2 §7.2 "additive; admin requires write". One table beside the role matrix keeps the two from drifting. |
| 3 | Where tokens work | Organisation and project routes, plus a short list of account reads (`/me`, `/orgs`, profiles, general settings) and the user's own `/tokens`. Platform routes, session management, recovery codes and device approval are browser-only (403 `token_not_allowed`), and a platform admin's token has no platform powers. | A leaked token should not reach the platform; the spec says the platform admin can't see tokens. |
| 4 | Project restriction | A restricted token can see only its projects (others are 404, as for anyone who can't see them) and can act at the organisation level only to view it (403 `insufficient_scope` otherwise); lists are filtered to its projects. | V2 §7.2 "can't see or act on anything else". |
| 5 | Destructive actions | No step-up auth for tokens; routes that need it in the browser need the `admin` scope and the existing typed `confirm` (delete project, restore in place, delete org), plus `confirm` added for transferring ownership. Moving a project to another org can't be done with a token (it spans two orgs). | V2 §7.2. |
| 6 | Tokens creating tokens | Allowed with `write`, never wider than the caller: scopes, projects and expiry at most its own. | CI can rotate its own token without a browser, but can't escalate. |
| 7 | Revocation | Tokens are revoked when their user leaves or is removed from the org or is disabled, and stop working when the org is deleted; a project moved out of an org leaves its restricted tokens (emptied ones are revoked). Suspension disables, rather than revokes, an org's tokens (403 `org_suspended`), so reinstating restores them. | V2 §3.4, §10.8. |
| 8 | Rate limits | Per token 600 and per organisation's tokens 1,200 requests a minute, in-process sliding windows; 429 with `Retry-After`. Failed bearer authentication is not separately limited (a 256-bit token can't be guessed). | V2 §7.2 "rate-limited per token"; per server, like the other limiters. |
| 9 | Last used and audit | `last_used_at`/`last_used_ip` are updated at most once a minute; audit rows from tokens carry actor kind `token` and the token id. | V2 §7.2, §2.7. |
| 10 | Device login | RFC 8628-style: `POST /auth/device` returns a 32-byte device code and an 8-letter user code (no vowels) valid 10 minutes; the approval page lets the user pick the org and narrow (never widen) the scopes; the token is sealed with the master key until the CLI's next poll collects it, once. Polling faster than every 2.5 s answers `slow_down`. | The CLI never sees a session, and a code read over someone's shoulder is only useful for 10 minutes and only to them. |
| 11 | Emails | On creation, and once when a token is within 7 days of expiry (the hourly token sweep). | V2 §7.2. |
| 12 | Platform maximum | Settings key `tokens.settings` (`max_days`, 1–365, default 365); non-expiring tokens are not offered. | V2 §7.2; open question 7 left at the 1-year maximum. |
| 13 | CLI | `cmd/cli` builds `pgdock` on an oapi-codegen client (`internal/api/client`, checked by `make check-generated`), standard library flags (no framework), BurntSushi/toml for the config. `PGDOCK_TOKEN` and `PGDOCK_SERVER` override the saved context for CI; `token_cmd` reads a token from a password manager. `connect` caches the personal login in `credentials.toml` (0600) because the password is shown once. | V2 §7.1. |
| 14 | Deferred | `branch`, `webhooks`, `jobs` and `demote` commands arrive with their milestones (M13–M15). | Scope. |

## M11 — Visual table editing

| # | Topic | Decision | Why |
| --- | --- | --- | --- |
| 1 | Filters | Repeatable `filter` query parameters, each a JSON object (`column`, `op`, `value`/`values`); columns are checked against the catalog and quoted, values are always bind parameters (text, cast by Postgres to the column's type). `contains` is `strpos(lower(col::text), lower($n)) > 0`, so no LIKE escaping; `in` is `col = ANY($n)` with a quoted array literal. A value that doesn't fit the column is a 400 with the Postgres error. | V2 §4.1 "parameterised, never string-concatenated". |
| 2 | Paging | Keyset on the primary key when unsorted or sorted by a single-column key (either direction); any other sort pages by offset with the key as tiebreak, warning past 10,000 rows. Tables without a key page by ctid, views by offset. | V2 §4.1. |
| 3 | Editability | Plain tables with a primary key, when the project console isn't read-only and the user's role is developer or above (a new `project.table_edit` action, `write` scope for tokens). Views, materialised views, partitioned parents, foreign tables and key-less tables are read-only, with the reason in the UI. | V2 §4.2, §2.3 "Table editor — rows and schema". |
| 4 | Conflicts | Each editable row carries `xmin::text`; updates and deletes add `AND xmin::text = $n` and return the new xmin. Zero rows affected rolls the whole save back and answers 409 with the row as it is now (or that it was deleted); the UI offers re-applying the edit on top of it or discarding it. | V2 §4.2 "no silent overwrites". |
| 5 | Saves | One transaction with `SET LOCAL statement_timeout = 30s, lock_timeout = 5s`, at most 500 changes; a refused change is a 422 naming it, with the Postgres error, and nothing is saved. Generated and identity columns can't be written. The audit row records the table and the summary ("3 updates, 1 insert"), not the values. | V2 §4.2. |
| 6 | Schema planner | `internal/schemaedit` is pure: a change plus a `State` the console reads from the catalog (size, rows, the column's current type and default, whether a type change rewrites, whether a default is volatile, a dropped object's definition) gives DDL, risk notes, a reverse, and a hash. Identifiers are quoted; types must match a strict pattern and `to_regtype`; expressions (defaults, checks, index predicates, USING) are SQL and run as the owner role, who could run them in the console anyway. Each statement runs through the extended protocol, so one statement can't smuggle another. | V2 §4.3. |
| 7 | Rewrite detection | Same type with a wider (or removed) length or precision, or a binary-coercible cast (`pg_cast.castmethod = 'b'`, e.g. varchar → text), doesn't rewrite; anything else does. The note is a warning, or danger from 100 MB; it shows the table's size. Volatile defaults are detected by the volatility of the functions they call. | V2 §4.3 examples. |
| 8 | Preview then run | Running a change needs the preview's hash: if the SQL it would run now differs, the answer is 409 `stale_plan`. Drops (tables, columns, schemas, constraints, indexes) need the name typed, and with a token the `admin` scope. | V2 §4.3 "every schema change previews its SQL". |
| 9 | Execution | `SET lock_timeout = 5s` (statement timeout 10 minutes for rewrites); transactional statements run in one transaction; `CREATE INDEX CONCURRENTLY` (the default) and `ALTER TYPE … ADD VALUE` run alone. The audit row holds the SQL. Afterwards the read-only role's grants are re-applied. | V2 §4.3. |
| 10 | Migrations | Plain SQL (Down as comments), goose (`-- +goose Up/Down`, `NO TRANSACTION` for concurrent builds, StatementBegin/End around statements with inner semicolons), and dbmate (`-- migrate:up transaction:false` when needed). The Down is generated where the reverse is unambiguous (drop what was added, reverse a rename, restore an old default or type, re-add a dropped constraint or index from its definition) with `TODO` comments elsewhere. Filenames are `YYYYMMDDHHMMSS_<slug>.sql`. The chosen format is remembered per user and project (`editor_preferences`). | V2 §4.3 "Save as migration". |
| 11 | Exports | CSV or JSON of the filtered, sorted rows, at most 100,000, streamed; whether rows were left out is the `X-PGDock-Truncated` trailer. Exports, saves and schema changes count against the org's concurrent console limit. | V2 §4.1, M11 "console concurrency limits apply". |
| 12 | Deferred | Editing views, functions, triggers, RLS and partitioning; schema diffs; migration history; a date picker beyond typed inputs with placeholders; the FK picker searches by typing the key (the side panel shows the referenced row). | V2 §4.4; scope. |

## M12 — Backup storage targets

| # | Topic | Decision | Why |
| --- | --- | --- | --- |
| 1 | Ownership | `storage_targets.org_id` (NULL: platform). Names are unique among the platform's targets and within each organisation. Deleting a target keeps its row (backups reference it) with the credentials wiped; organisation deletion doesn't touch org targets. Org target queries filter by `org_id`, so another organisation's id is a 404, and the platform admin's list and backup listings outside the organisation say only "an org target". | V2 §6 "invisible to other orgs and to the platform admin". |
| 2 | Live test | Write, read back, list, delete a random object under the prefix; saving (create or edit) stores nothing unless every step passes, and answers the steps either way. Empty access or secret key on an edit keep the stored ones. | V2 §6 "saving is blocked until it passes". |
| 3 | Project choice | `projects.storage_target_id` NULL follows the platform default, so changing the default moves every project that never chose. Each `backups` row keeps its own `storage_target_id` and is read from there, so a switch never strands a backup. A shared project switches at once; a dedicated one (or a copy) is a `storage_switch` operation. | V2 §6 "existing backups keep their storage_target_id". |
| 4 | Per-project keys | `backup_keys` holds a 32-byte secret sealed with the master key; the project's OpenPGP key (Curve25519) is derived from it with HKDF, the same way WAL-G's instance key is. Logical backups with a project key are standard OpenPGP messages (SEIPD with MDC, AES-256, no compression: pg_dump compresses) written by the agent to the public key, as `.dump.gpg`; `backups.encryption_key_id` says which key. Backups without one stay in the PGDock format under the instance key. Rotating retires the old key; its backups still open with it. | V2 §6 and the M12 done-when: "restored with standard tools using only the downloaded key" — gpg and pg_restore, no PGDock. |
| 5 | Key download | `GET /projects/{id}/backup-key/download` (project admins, re-authentication, audited like a mutation) returns the armored private key after a README; gpg ignores the text before the armor, so the file imports as is. | V2 §6. |
| 6 | Dedicated | The instance records where it archives (`walg_target_id`, `walg_key_id`, `walg_prefix`). A switch of target or key moves WAL-G to a new prefix (`instances/<id>/wal-g-<hash>`), recreates the container with the new environment (a restart), and takes a base backup at once. Base backup rows record their prefix, target and key, so recovery from an older one reads the old archive; those expire 7 days after the switch, and the archive is deleted with the last of them. The scheduler re-checks each running dedicated project and reconfigures any whose archive no longer matches its target and key (the platform default changed, a key was enabled). Point-in-time recovery fetches WAL with the source archive's own settings from a 0600 file that `recovery_end_command` removes, not the new instance's. | V2 §6 "switching reconfigures WAL-G and takes a fresh base backup immediately". |
| 7 | Copy existing | Logical, final and safety backups not already on the new target are streamed by the control plane from their target to the new one, hashed on the way and read back; each must match the backup's recorded SHA-256. The copy is a new `backups` row (`copy_of`) with the original's times and key; the original becomes `copied` (not listed for restore, still counted) until deleted, which happens only with `delete_originals`, or when retention removes the copy. Base backups stay with their archive. | V2 §6 "verified by checksum; originals are deleted only if the user explicitly chooses". |
| 8 | Quota | `backup_storage_mb` usage is the size of live (succeeded or copied) backups on platform targets; org targets never count, in quotas or in usage records. A manual backup to a platform target over the limit is 409 `quota_exceeded`; nightly backups keep running, so a full quota never leaves a project without backups. | V2 §6, §10.3. |
| 9 | Deleting targets | Refused (409 `target_in_use`) while a live project or dedicated instance uses it, and the default can't be deleted; with unexpired backups it needs `accept_unrestorable=true`, which marks them deleted. The bucket is never emptied. | V2 §6. |
| 10 | Transfers | A project using its organisation's target, or holding backups there, can't be transferred out until it is back on platform storage (copy with delete-originals). | An org target serves only its own organisation. |
| 11 | Deferred | An organisation-wide default target; moving base backups between targets; per-target retention; client-side key escrow. | Scope. |

## M13 — Branching

| # | Topic | Decision | Why |
| --- | --- | --- | --- |
| 1 | Model | A branch is a project with `parent_project_id`, always on the shared tier (the org's own shared cluster if it has one), with `branch_source`, `branch_schema_only`, `expires_at` and `sensitive_data` (§11). Its database and role get opaque names like every project since M9, not `<parent-db>__<slug>`; the name the user gives is the project name. It starts with the parent's project members and roles; its creator becomes its admin. | V2 §8.1; M9 opaque naming. |
| 2 | Create | `branch_create` reuses provisioning (prepare, publish, rollback on failure): the parent's extensions in `public` are created first as the admin, then the data comes from the parent's latest logical backup (`pg_restore`, with `--schema-only` when asked) or live (`pg_dump | pg_restore` on the branch's agent, as promotion does). | 3 | Reset | `branch_reset`: pooler `KILL` (clients wait), drop and recreate the database with the same role and verifier, refill from the parent (the branch's own source by default), re-sync members' roles, `RESUME`. | 4 | Expiry | Default TTL 7 days, 1 hour to 30 days or none (`ttl_hours: 0`). A sweep every 10 minutes deletes branches past `expires_at` (paused while the org is suspended) and emails the creator once when less than 24 hours remain; moving the expiry re-arms that email. Branch deletes skip the final backup unless the branch takes backups. | V2 §8.4. |
| 5 | Permissions | A new `project.branch` action (developer and above, `write` token scope) covers create, reset and detach; `DELETE /projects/{id}` on a branch checks it instead of `project.delete`, so developers delete branches but not projects. A full-data branch of a sensitive project needs the project admin role. A token restricted to a project covers its branches, so a CI token can create, use and delete them. | V2 §2.3 "Create / reset / delete branches"; §8.5. |
| 6 | Quotas | `branches` (Personal 10, Team 25) counts live branches; branches don't count toward `projects`. Creating one checks the parent's latest measured size against `project_storage_mb` and the org's shared storage plus that size against `shared_storage_mb`, then operations in flight. | V2 §8.2 step 1, §10.3. |
| 7 | Usage | Hourly `branch_hours` (the fraction of each hour a branch existed) and `branch_gb_hours` (its measured size), besides its shared-storage GB-hours. | V2 §10.9. |
| 8 | Limits | One level deep; branches can't be promoted (detach first) and skip the nightly schedule unless `branch_backups`; a parent with live branches can't be deleted. | V2 §8.4. |
| 9 | CLI and CI | `pgdock branch create … --env` prints `DATABASE_URL`, `DATABASE_URL_SESSION`, `PGDOCK_BRANCH_ID` and `PGDOCK_BRANCH`; `--replace` deletes a same-named branch first, which gives a fresh branch per push. `docs/examples/github-actions-branch.yml` is parsed and its steps run with bash by the integration suite. | V2 §7.1, M13 done-when. |
| 10 | Deferred | Data masking; branches of branches; branching a dedicated parent from its WAL-G base backups (live works). | V2 §17. |

## M14 — Demotion

| # | Topic | Decision | Why |
| --- | --- | --- | --- |
| 1 | Preflight | `POST /projects/{id}/demote/preflight` returns the seven checks of V2 §5.2 (size, extensions, roles, allowance, connections, settings, capacity) as ok, warning or blocked, with the estimated freeze, the chosen cluster, and the settings afterwards. `POST /projects/{id}/demote` runs them again and refuses (409) while any is blocked, or while there are warnings and `accept_warnings` is not set; the operation runs them a third time against the chosen cluster before it touches anything. | V2 §5.2 "run as a preflight and again at the start of the operation". |
| 2 | Checks | Size: the database against `project_storage_mb`, and the org's shared storage plus it against `shared_storage_mb`. Extensions: anything outside the shared allow-list. Roles: any non-superuser role on the instance other than the owner, `_ro`, the console's and members' logins (including the NOLOGIN stand-ins a promotion of an imported project created). Connections: the most active plus idle backends at one time in the last 7 days of metrics against the shared connection limit (a warning). Settings: database-level settings and the owner's own role settings beyond PGDock's guardrails (a warning; `pg_dump` doesn't carry them). Capacity: the org's eligible shared clusters, those with node free disk (latest metrics; unmeasured counts as room) for the size plus 20%, the most free first. | V2 §5.2. |
| 3 | Flow | Mirrors promotion: the database, owner role (same SCRAM verifier) and members' logins on the shared cluster with the shared hardening; freeze (NOLOGIN, pooler `PAUSE`/`KILL`, end sessions); `pg_dump \| pg_restore` by the shared cluster's agent; verify rows and sequences; cut over in one transaction; `RESUME`; a logical backup; stop the dedicated container. A shared copy a recent promotion kept (same names) is dropped first. | V2 §5.3. |
| 4 | Rollback | Before the cutover: LOGIN restored and the route resumed on the dedicated instance, the partial shared database and its roles dropped. After it, the operation finishes forward. | V2 §5.3. |
| 5 | Retention | The stopped instance is a `retired_databases` row with reason `demotion`; the hourly cleanup destroys its container and volume after 48 hours (not the WAL-G archive). Until then it still counts in `OrgDedicatedUse`, so the allowance is released when it is destroyed, and the orphan reaper leaves it alone.
