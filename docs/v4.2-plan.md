# Release 4.2 build plan: emails, legal pages, brand, sign-in screens

Status: **decisions settled; build starting with the logo.**

V4.1.0 is the first Xenibase release and it is on production. 4.2.0 is the
first release that looks like a product a business would pay for: the
emails, the legal pages and the sign-in screens. It also carries the fixes
already merged or open since the tag: the install guide and the V2
runbook, the upgrade rehearsal, and the wallet panel's "Get the bank
account" button (PR #50).

It is a minor version because it adds features. It is tagged only after the
checks at the end are green.

## What I found

| Area | Today |
| --- | --- |
| Email | 20 call sites each build a plain-text string (`mail.Message{Subject, Body}`). `internal/mail` renders `text/plain` only. No layout, no logo, no HTML. |
| Project auth email | `internal/services/authmessage.go` and `authconfig.go` send email *for customers' own apps*. Different audience from the platform's email; see decision 5. |
| Legal page | `web/src/pages/Legal.tsx` prints `body_md` inside a `whitespace-pre-wrap` box. The same happens for the terms and privacy notice (`TermsText` in `components/Layout.tsx`, used by sign-up and "the terms have changed"). The web app has no markdown renderer. |
| Logo | `components/shell/Logo.tsx` is a purple database cylinder. `web/public/favicon.svg` is still PGDock's: a blue square with a "P". There is no Open Graph image, no touch icon, no brand page. |
| Palette | `web/src/styles.css`: dark-first, purple accent `#7c3aed`, light theme available. Invoice PDFs (`internal/billing/pdf.go`) and the docs site have their own styling. |
| Sign-in screens | `AuthShell` with a quiet brand panel. `/` redirects to `/projects`, and that stays. |

## Decisions (settled)

1. **Brand.** No reference. Three logo directions are drawn for the owner to
   pick from; the story is a place where your data lives safely and is easy
   to reach.
2. **Home.** The sign-in, sign-up, verify, reset and invitation screens
   only. **No change to any redirect or flow:** `/` still goes to
   `/projects`, and the same routes, forms and test IDs stay. No landing
   page, no dashboard redesign.
3. **Voice.** Readers are business people and developers. The tone is
   warmer: plain words, no jargon where a plain word works, friendly but
   not chatty, and still exact about amounts, dates and what to do.
4. **Sending domain.** Verified in Resend. The From name and reply-to are
   set in Settings → Email.
5. **Customers' own app emails.** Restyled: the five auth emails (confirm,
   magic link, reset, invitation, email change) get a neutral layout in the
   *customer's* name, with no Xenibase logo. A project's own subject and
   body still work and are wrapped in the same layout; a per-project switch
   turns the layout off.

## Workstreams

The order matters: the brand comes first, because the emails and the sign-in
screen both use it.

### A. Brand foundations (first, about 2 days)

- A single source of truth for the brand: name, colours, fonts, logo files,
  in one `brand/` directory that the web app, the emails, the invoice PDFs
  and the docs site all read.
- Logo: a mark and a wordmark, in colour, on dark, on light, and one-colour.
  SVG masters, plus PNGs (email clients can't show SVG), a favicon set
  (`.svg`, `.ico`, 180px touch icon), and an Open Graph card (1200×630).
- Replace the stale PGDock favicon; update `Logo.tsx`, `index.html` and the
  invoice PDF header.
- A short brand page in `docs/` (colours, spacing, do and don't) so the
  next change doesn't drift.
- Tokens: keep dark-first, tune the accent and surface colours to the new
  direction, and check contrast (WCAG AA) in both themes.

### B. Email (about 4 days)

- `internal/mail` gains HTML: `multipart/alternative` with a plain-text part
  (so a message is readable everywhere and spam filters are happy) and an
  HTML part.
- One responsive layout, table-based with inline CSS because that is what
  Outlook and Gmail render: header with the logo, a content block, a button,
  a quiet footer (company name, address if you want one, "why you got this").
  Dark-mode friendly (transparent-safe logo, no pure-white backgrounds
  forced). Logo is a hosted PNG on a public path of the app, not
  an attachment.
- The five **project auth emails** (decision 5) get a second, neutral
  layout in the customer's name, using the project's site name and no
  Xenibase logo, wrapping the customer's own text where they have
  overridden it, with a per-project switch to turn the layout off.
- Typed templates instead of strings at 20 call sites: verify email, reset
  password, invitation, security notices, invoices and receipts, payment
  failed and dunning, wallet funded, low balance, forecast and spend
  alerts, Free-tier pause warnings, maintenance and incident notices,
  support, backup and alert emails. Each gets a subject, preheader, title,
  body paragraphs, an optional call to action and optional facts table (an
  invoice's amount, date, number).
- Copy rewritten in the chosen voice, short and specific: what happened,
  what to do, by when.
- Everything user-supplied (organisation names and the like) is HTML-escaped;
  tests prove it.
- Tooling: a golden-file test per template (HTML and text), a `mail
  preview` command that renders every template to files, and an admin
  "send me a test of each" so you see them in your own inbox in Gmail and
  Apple Mail (I can't see Outlook; you'd check that one).

### C. Legal and terms pages (about 1 day)

- Render markdown properly: headings, lists, tables, links, in the app's
  type and theme. A renderer that never injects raw HTML (so a document
  can't script the page), with GitHub-style tables for the SLA's tables.
- Apply it to every place a document is shown: Org → Legal, the terms in
  sign-up, and "the terms have changed". Keep the accept flow, versions and
  test IDs as they are.
- A readable layout for business readers: a contents list for long
  documents, a version and date line, print and "download PDF" buttons.
- The template documents themselves get a read-through for plain language
  (`internal/legal/defaults.go`). I'm not a lawyer: someone qualified should
  review the final text before real customers sign it.

### D. Sign-in and sign-up screens (about 2 days)

Only the screens a visitor sees before they are signed in: sign-in,
sign-up, verify email, reset password, invitation, and the setup wizard's
first page. They share `AuthShell` (`components/Layout.tsx`), so most of
this is one component.

- A new brand panel and layout, in the new brand, light and dark, phone to
  desktop.
- Warmer copy for every heading, hint and error on those screens, shown to
  you as a list before it ships.
- **Unchanged:** the routes, the redirects (`/` to `/projects`), the forms'
  fields and validation, two-factor and the e2e test IDs. The Playwright
  journeys must pass untouched, apart from copy they quote.

### E. Things that ride along (about 1 day)

- Merge PR #50 (the bank-account retry button).
- Point the upgrade rehearsal at `v4.1.0` (it is now a release), which also
  makes 4.2.0 the first real upgrade of a Xenibase install.
- `CHANGELOG.md` under `## v4.2.0` (the release workflow reads that
  heading), install and upgrade docs.

## How each part is tested

- Emails: golden HTML and text per template; escaping tests; a link check
  (every URL points at the configured public URL); the existing tests that
  assert on email text are updated rather than loosened.
- Legal: component tests with the real default documents; the e2e journeys
  that read `legal-text-*` and `terms-text` updated.
- Brand and the sign-in screens: type-check, lint, the Playwright e2e
  (unchanged apart from quoted copy), plus screenshots at
  phone, tablet and desktop widths in both themes that I'll show you.
- Everything: CI green on `main`, including the `upgrade` job (a real
  upgrade from 4.1.0, with a rollback test in between).

## Release

1. Merge the workstreams to `main` as separate PRs, each with CI green.
2. A staging pass: send every email to yourself, click through the legal
   pages, sign up from scratch, walk the sign-in screens.
3. Add `## v4.2.0` to the changelog, tag `v4.2.0`, and let CI run on the
   tag. The tag is only used for production if every job is green,
   including `upgrade`; the Deploy workflow checks this itself.
4. Deploy with the Deploy workflow (or `upgrade.sh` on the server). It backs
   up first and rolls back by itself if the new version isn't healthy.

## Risks

- **Email clients differ.** Outlook's renderer is the worst. Table layout
  and inline CSS are the answer, and I can't test Outlook myself.
- **Brand taste is subjective.** The three-options step in A is there so you
  choose, not me.
- **Copy touches many files.** Copy is shown as a list for approval, so
  nothing changes silently.
- **Legal wording is yours.** Better rendering doesn't make the documents
  reviewed.

## Not in 4.2

Marketing site, blog, in-app chat, localisation, email unsubscribe
management (these are transactional), and the wallet reversal handling
(tracked in [iswallet](iswallet.md)).
